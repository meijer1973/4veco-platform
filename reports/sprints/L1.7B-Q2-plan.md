# Sprint L1.7B-Q2: Exit Ticket Target-Equivalent Implementation Plan

Date: 2026-06-01

Status: planned active. This file selects the first implementation target and
defines the implementation route. It does not itself edit source exit-ticket
data, regenerate lesson output, or authorize product use.

## Goal

Prepare `L1.7B-Q2` to implement the first target-equivalent exit ticket under
the corrected product specification.

This plan selects `1.1.2 Percentages en indexcijfers` as the first candidate
because the lesson roadmap recommends it, it has no existing advisory
short-check source that would need to be preserved as a second surface, and the
current shared task shell already supports the required calculation,
final-answer, notation, and short-response families.

The implementation target is a separate target-equivalent exit ticket for
`1.1.2` that checks the same operation chain as the paragraph target exercise:
percentage change, price-index calculation, index-to-index percentage change,
and the D31 distinction between index points and percent. The later rendered
output must remain non-summative and may not use paragraph-completion language
until `GATE-L1.7B-Q2` approves it.

## Context

`CHECK-Q2-PLAN` closed planning/preparation with flags. It confirmed that no
current `1.1.1`, `1.1.2`, or `1.1.3` output is target-equivalent proof. It
also required any later `L1.7B-Q2` work to select one paragraph and resolve or
explicitly scope that paragraph's blockers before implementation.

The source audit for this plan found:

- `1.1.1` already has `source-data/book-1/exit-ticket/1.1.1.json` as an
  advisory `Korte check` with `targetReadinessEvidence: false`; implementing
  a separate proof ticket there would first require dual-surface generator
  work and an A98 versus held-evaluation decision.
- `1.1.2` has no current exit-ticket source file and is the roadmap's
  recommended first paragraph for Q2, but D31 must be explicitly checked.
- `1.1.3` remains blocked by graph-axis repair and A81 source-use plus
  underlying answer-form coverage.

The current `ExitTicketEngine` can wrap `task_shell` tasks, but
`calculation_work_capture`, `short_constructed_response`, and
`structured_reasoning` are currently self-check families. The implementation
must not pretend generic self-check is target-equivalent proof. It must either
add deterministic or rubric-backed proof handling for the `1.1.2` chain, or
pause before setting proof metadata.

Current shell and landing copy also still use advisory language such as
`Korte check` and `Kies wat je nog wilt oefenen`. The implementation must
repair or explicitly scope that copy before rendered output can be reviewed as
a target-equivalent exit ticket.

## Quality Standard

The quality floor is a source-controlled implementation plan that can lead to
rendered output and proof evidence where a student performs the same cognitive work as the
`1.1.2` target exercise and receives neutral local feedback without diagnostic,
mastery, sequencing, summative, AI, PV, Scale Gate, or product-use claims.

The specification requirements being fulfilled are:

1. target-equivalent exit tickets are separate from advisory short checks;
2. the chosen exit ticket must cover the full reviewed target-exercise
   operation and answer-form chain;
3. calculation work, final answer, notation, and D31 explanation must use task
   families that actually fit the target work;
4. completion language remains blocked until `GATE-L1.7B-Q2`;
5. all implementation evidence must be reviewable remotely before any human
   gate.

The review gate that will judge student-facing quality is
`GATE-L1.7B-Q2`. This sprint plan only prepares the implementation route. Any
omitted requirement is named as a blocker or follow-up before source edits.

## Operationalized sprint procedure

1. Record baseline evidence and paragraph selection. Stop if the selected
   target exercise is not present or if `1.1.2` already has unreviewed
   exit-ticket source data.
2. Ask the planning/review subagent to review the paragraph selection, current
   generator/engine capability, D31 blocker, planned artifacts, and stop
   conditions before implementation edits. Fix this plan if review finds a
   core gap.
3. Define the `1.1.2` operation chain, expected answers, task-shell mapping,
   answer-model criteria, state/metadata contract, and generated-output plan.
   Stop if D31 cannot be represented without
   generic self-check pretending to be proof.
4. Define the source-data and engine contract. Decide explicitly whether the
   implementation must add deterministic final-answer matching for
   `calculation_work_capture`, rubric-backed short-response checking, or a
   gate-held proof status.
5. Only after the plan passes planning review, implement source and engine
   changes through source-controlled files. Do not hand-patch generated output.
6. Regenerate only through platform build/deploy routes and inspect live
   rendered output. Stop if the route cannot show the full task sequence,
   feedback states, mobile/narrow state, and dark mode.
7. Run teacher-learning-quality, student-experience, accessibility, testing,
   and lead-review checks. Stop if any review finds missing operation-chain
   coverage, confusing short-check/proof language, or forbidden authority
   claims.
8. Prepare `GATE-L1.7B-Q2` only after evidence is committed and pushed. The
   human gate must decide completion language separately.
