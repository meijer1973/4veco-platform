## Authority And Scope

This subordinate roadmap governs the Golden Exercise Workbench rollout. The
product end-state, companion specifications, active reference-team roadmap,
`REV-STD-1`, and later exact-head human decisions remain controlling.

The owner decision on platform PR #148 closed Scale Gate 1 narrowly as
`PASS_CONTROLLED_ROLLOUT`. That decision makes the six current first-three
check surfaces eligible for explicitly governed rollout waves. It does not
itself authorize actual route adoption or rollout.

The following remain held and require separate current evidence and authority:

- actual rollout or product-route adoption;
- automatic repository-wide migration;
- target-equivalent completion language;
- diagnostics, mastery/sequencing, adaptive routing, PV, or summative use;
- broad product use or student/product use.

## Current Renewal

`Y1-GOLDEN-ROLLOUT-WAVE-1` renews the workflow-availability guard from current
`main`. It supersedes the stale implementation in platform PR #205 and must:

- verify exactly the six first-three surfaces;
- compare committed changes using exact event base/head Git ranges;
- reject protected source, engine, generated lesson, and authority drift;
- fail on missing or escaping routes and stale rendered evidence;
- use dedicated negative tests;
- refresh repository maps, indexes, and the internal dashboard;
- route as L4 `READY_FOR_HUMAN_REVIEW` with exact-head evidence.

This renewal is evidence and governance work. It changes no exercise source,
engine behavior, generated lesson output, target-readiness flag, or route.

## Non-Negotiables

- Golden Workbench is route architecture, not a CSS label.
- Golden pages use a direct Golden root and do not revive legacy or hybrid
  exit-ticket shells.
- Advisory checks remain local practice advice only.
- Exit tickets remain bounded target-readiness evidence only.
- `PASS WITH FLAGS` may not carry a missing core requirement.
- Review packets cite product end-state and original gate specifications, name
  non-negotiables, include a core checklist, classify findings, and record
  `blocks`, `does_not_block`, and `proof_required_to_close` for carried issues.
